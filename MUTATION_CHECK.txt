FOCUSED MUTMUT CHECK — ONCE BEFORE SUBMISSION

Purpose: test whether assertions catch a changed business rule. This is a small
release check, not a whole-project mutation campaign or an automatic CI job.
Keep the application and stakeholder value central.

1. Choose the environment
Use Codespaces (recommended for a consistent Linux environment), macOS, or
Linux/WSL. Native Windows PowerShell cannot run this mutmut version; Windows
students should open their project in Codespaces or an existing WSL environment.
Do not run it on Render or against live Neon. Use isolated test settings/data.
Keep your existing application dependencies, interpreter and normal test runner.

2. Install separately from production/CI dependencies
The commands below were exercised in Codespaces with mutmut 3.5.0. This release
requires Python >=3.10. First inspect your configured environment:
  python --version
  python -c 'from importlib.metadata import version; print(version("mutmut"))'
If mutmut is absent, the second command raises PackageNotFoundError. If 3.5.0
is already installed and the app/test dependencies work, reuse that environment.
If another version is installed, preserve it: use a separate optional mutation
environment rather than downgrading shared tools. From your application folder (project/ for all five current teams):
  python -m venv /tmp/sprint3-mutation-env
  /tmp/sprint3-mutation-env/bin/python -m pip install -r requirements.txt
  /tmp/sprint3-mutation-env/bin/python -m pip install "mutmut==3.5.0"
  /tmp/sprint3-mutation-env/bin/python -m pip check
If your team has a separate development file, install it too. The dependency commands are examples: use your existing locked install commands
or actual dependency files. Do not create empty files or replace existing pins.
Verify the selected tests pass in this environment before mutation testing.
Use an unused environment path; /tmp is disposable, so save evidence in your
project or submission. This optional tool environment is an exception to the
normal instruction to reuse your configured Codespaces app environment.
For that environment, replace python and mutmut in the remaining examples with
/tmp/sprint3-mutation-env/bin/python and /tmp/sprint3-mutation-env/bin/mutmut.
For Poetry/uv/Pipenv use the established equivalent optional tool group/run
commands. Do not add mutmut to Render's dependencies or automatic CI installs.
Do not upgrade app dependencies or Python solely for this check. For Python
below 3.10, use a compatible release and its own documented command syntax;
the 3.5.0 examples below are not verified for older mutmut versions.

3. Select a small real scope
Choose one short business-rule function and a small set of relevant fast tests.
Use real app code, not the supplied reporter or synthetic examples. First make
sure those tests pass unchanged. Mutmut 3 uses pytest internally; your regular
CI may keep Django's test runner. Existing unittest-style tests can be collected
by pytest. Django-dependent tests need compatible pytest-django and the project's
isolated test settings; prefer a pure business-rule function when appropriate.
Example baseline (replace the path with your actual test file):
  python -m pytest tests/test_rules.py -q
If pytest reports zero tests or a setup error, fix selection/setup before mutmut.

4. Configure inside project/ (beside manage.py and pytest.ini)
All five current teams use this layout. Merge into project/pyproject.toml:

[tool.mutmut]
paths_to_mutate = ["core/"]
do_not_mutate = ["*/tests/*", "*/tests.py", "*/test_*.py", "*/migrations/*"]
also_copy = ["config/", "manage.py", "pytest.ini", "templates/", "static/", "gen/", "tests/"]
pytest_add_cli_args_test_selection = ["core/"]

Then narrow test selection to the relevant existing file(s) where feasible.
Team 4 also has project/tests/: select the needed files there, not just core/.
Merge rather than duplicate [tool.mutmut]. Keep the existing pytest.ini; it
already loads Django settings and includes tests.py discovery. Keep isolated
test settings/data; DJANGO_SETTINGS_MODULE=config.quality_test_settings may be
set using TEAM_COMPATIBILITY.txt. config/ is copied into the mutation workspace.
Copying manage.py is essential: otherwise pytest-django may find the original
parent project and test unmutated code, reporting every mutation as "no tests".
Templates/static/gen are support data for view/image tests; absent optional
folders are ignored. Never copy credentials or live databases.
Do not add an absolute pythonpath/PYTHONPATH pointing at the original project.
If tests pass normally but fail only under mutmut, inspect missing support files
and imports before changing business logic or tests. If the baseline already
fails normally (currently Team 4), fix that baseline first.
This config generates mutations for core/, but the filtered command below RUNS
only the selected function's mutants. Tests/migrations are excluded from mutation.

5. Run only the chosen function and inspect results
Commit your intended code/tests first and record:
  git rev-parse HEAD
  mutmut run --max-children 2 "core.your_module.x_your_function__mutmut_*"
  mutmut results
  mutmut show core.your_module.x_your_function__mutmut_1
  mutmut browse
For this pinned release, generated names contain x_ before the function and
__mutmut_ before the number. A plain module.function* filter matches nothing.
Replace the module and function in the example; keep x_ and __mutmut_*. The
show command needs an exact mutant name from results, not necessarily _1.
For class methods or other layouts, use the actual generated names from results.
If a filter reports "nothing matches", generation has already occurred: run
mutmut results, choose the intended function's names, correct the filter and
rerun it. Do not drop the filter and accidentally mutate the entire project.
The two-worker limit suits a small Codespace. Keep the quotes so the shell does not expand the wildcard. Inspect the listed names and confirm
that mutations were actually generated for the intended function. A zero-mutant
run is not evidence: correct the source path/filter or select suitable logic.
Use show for a text diff or browse for the interactive view. Press q to exit
browse; results/show work without a terminal UI. Inspect the changed expression
and its outcome. Do not use apply or commit deliberately mutated source. Keep generated mutants/ out of Git.
If the check is too slow, stop it and select a smaller function/test set; report
the scope actually completed, not a partial run as a whole-project score.
Some decorated functions are skipped in 3.5.0. Select a generated helper/method
with meaningful tested behavior; never remove a safety/request decorator just
to make mutation testing run. Team-specific notes are in TEAM_COMPATIBILITY.txt.

6. Interpret and retain a small amount of evidence
Killed: a test failed and detected the injected change.
Survived: selected tests passed despite the change; investigate a missing
assertion, missing case, or a change that does not alter meaningful behavior.
Timeout/error/untested: report separately, investigate setup/runtime issues;
these are not proof a test detected a bug. Save counts as displayed, not an
invented percentage that silently excludes inconvenient outcomes. No target
mutation score and no requirement to eliminate every survivor.
Save a screenshot or text summary with command, tool version, commit, selected
function/tests, counts and one inspected mutation in your existing submission
or issue. If survivors exist, inspect one and strengthen a test or explain your
decision. If all are killed, explain one mutation and its detecting test.
After changing the selected code/tests, rerun the same filtered run command
and retain the updated results; verify ordinary CI for the final
version as usual. No rerun is needed merely because unrelated code changed;
record which version and scope your evidence covers.
This may satisfy the existing ONE quality decision instead of evaluating a
separate AI finding. Still retain the automatically generated AI report.
Mutation results are separate evidence; the supplied AI reporter does not ingest
them. No extra narrative report, automatic workflow, or deployment gate is needed.
